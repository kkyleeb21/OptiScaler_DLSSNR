# D18 发布后保留与清理流程

2026-09-14。后续开发以最新正式 release 的源码、标签和清单为基准。尚未并入正式版的任务成果必须作为独立差异保留，不能因升级基线丢弃。0.1.5 私测 ZIP 经用户明确同意退役；它不再是必须保留的安装包。

## 每次发布必须留下什么

1. 已发布 ZIP、源码提交/标签、逐文件 SHA256、发布附件回读结果；对应的发布版和诊断版身份必须明确。历史发布没有诊断版时记录“未单独生成”，不要补造。
2. 完整对应源码、构建配置/命令、依赖与 runtime 身份、私有符号 PDB、构建日志。NVIDIA runtime 不放入对外包。
3. 共同诊断工具的版本快照、事件/schema 文档、离线摘要入口、每个 API 的能力和未覆盖项。日常采集默认关闭、有界；研究宿主显式运行。
4. 上一个稳定版本的回滚包、每个实际部署游戏的配置/代理/runtime 身份和回滚记录。没有替代品或没有核对哈希的备份不得清除。
5. 每项重要结论的代表性完整证据：输入、输出、manifest、构建/runtime/配置身份、采样条件、原始日志和分析结果。完整短序列优先于零散截图；负例和失败尝试保留索引。

## 数据分层

| 层级 | 内容 | 处理规则 |
|---|---|---|
| 长期保留 | 正式源码/包/哈希，当前完整候选，回滚，报告，诊断工具/符号 | 不按时间或体积自动删除 |
| 可重建缓存 | 已关闭构建的 OBJ/PCH/IOBJ/IPDB | 对应源码、工具链、DLL/PDB 已保留并核对后，显式清单清理 |
| 原始采集 | RAW/RGBA16F、完整转储、反复采集 | 只有问题已收口、代表证据完整、摘要可追溯，且相关任务不再引用该原件，才列入下一次清理计划 |
| 重复副本 | 相同原始文件的额外拷贝 | 先逐文件哈希证明，并将每个引用更新至保留副本；不能仅凭名字/大小判断 |
| 进行中/并行任务 | 未合并研究、活跃游戏采集、另一任务的工作目录 | 全部保护，等待拥有该任务的交接 |

删除缓存会让下次构建变成全量编译，但不会影响保留 DLL 的运行。当前清理器只支持编译缓存和此次明确退役的 0.1.5 ZIP，**没有原始采集、转储、源码、DLL/PDB 或备份删除能力**。

## 每次收口的顺序

1. 发布/回读完成后确定新基线；未正式发布时只整理候选，不声称完成发布后验收。
2. 运行 `python tools/D18/render-toolkit.py storage -- --help` 查看盘点参数，生成只读体积清单。逻辑字节和硬链接唯一字节均不是保证可回收的物理空间。
3. 冻结要保留的源码/产品/证据清单，标出并行目录。确认待清理缓存不属于正在构建的目录；部署中的文件另遵循游戏退出与回滚规则。
4. 生成逐文件清单，记录绝对路径、用途、大小、SHA256、理由和保护的正式包/回滚产品。先运行 `apply-storage-cleanup.ps1 -Manifest <清单>`，默认仅验证。
5. 核对清单后加 `-Apply` 执行。工具拒绝越界、重解析路径、身份改变、重复条目和不支持的文件类型；先验证全部，再逐项重新核验删除并写收据。
6. 复核所有受保护哈希，记录删除文件数和逻辑字节，保留 manifest 与 receipt。清理中断时先核对逐项收据，不能盲目重跑旧清单。
7. 原始采集清理需要单独的证据退役清单和适用的安全实现。不要扩展为按后缀、日期或容量自动删除，也不要后台定时删文件。

本轮实际执行与大项建议见 `reports/D18_RENDER_CLOSEOUT_20260914/README_CN.md`。
